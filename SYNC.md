# Getting my fixes: `git pull`, not re-downloaded zips

The workspace is a git repository now (one commit per batch of work; `git ls-files | wc -l` tells you
how much is in it today). After every fix I re-create one file — **`lab.bundle`** — at the root, and you pull it. Your local notes and
exercise answers survive, nothing gets deleted, and there is no archive to unzip over yourself.

A bundle is just a git repo in a file. No account, no token, no network, works the same offline.

## 1. One time only: turn the code you already have into a clone

```powershell
cd C:\lab
git clone --branch main C:\lab\lab.bundle ip-tracking-lab
cd ip-tracking-lab\ip-lab
py tools\selftest.py            # RESULT: 166 checks passed
```

Verified exactly like this from a clean directory (clone the bundle, run the gate). If you would
rather keep the folder you already unpacked, clone into a second path and move your own notes across
— or better, start using the clone as the working copy from now on.

`git` comes with Git for Windows (<https://git-scm.com/download/win>); it also gives you the Bash
that `proxy_lab/chain_demo.sh` wants. Nothing else to install.

## 2. Every time I ship something

I publish a **complete** bundle by default (a few hundred KiB, applies to any clone at any state).
`tools/sync.py bundle --incremental` exists for when you pull often and care about size: it contains
only the newest commit, so your clone must already have the base — if `git pull` then answers
`Repository lacks these prerequisite commits`, that is the signal to ask me for a complete one.

```powershell
cd C:\lab\ip-tracking-lab
git pull C:\lab\lab.bundle main
py tools\selftest.py
git log --oneline -5                      # what just arrived
```

Expected: a `Fast-forward` line listing the changed files, then the selftest. `git diff HEAD@{1}
--stat` shows what moved since your previous pull if you want the details before you read them.

### 2b. If you have given me a credential, one command publishes both ways

```bash
cd /home/user && python3 ip-lab/tools/sync.py bundle --m "fix: ..." --push
```

`--push` runs after the bundle is written and verified: it pushes `main` and the tags to `origin`,
then reads `refs/heads/main` back off the remote and prints `origin/main at <sha> -> matches HEAD`.
If the push fails you get the bundle anyway and exit 1 - the file on disk is never invalidated by a
network problem, and a failed push is never reported as a publish.

## 3. If you have edited files and git refuses to pull

Commit your work first — this is your lab notebook, it deserves history:

```powershell
git add -A
git commit -m "notes: exercise 7 answers"
git pull C:\lab\lab.bundle main
```

Or `git stash` before the pull and `git stash pop` after. Both are non-destructive; `git checkout --
<file>` is not, so don't reach for that one.

## 4. Want it on GitHub too (backup, or a second laptop)

Your clone is an ordinary repo, so one-time bootstrap, no token pasted into any chat:

```powershell
cd C:\lab\ip-tracking-lab
git remote add origin https://github.com/<your-user>/ip-tracking-lab.git
git push -u origin main
```

Create the empty repo on GitHub first (no README, no .gitignore — those would make the first push
conflict). Git Credential Manager opens a browser sign-in and stores a proper credential in
Windows Credential Manager. Add the bundle remote alongside it and you keep both:

```powershell
git remote add bundle C:\lab\lab.bundle
git pull bundle main          # my fix
git push                      # your backup, whenever you feel like it
```

Two things to know before you make it public: `apps/shop.py` contains `JWT_SECRET =
"correct-horse-battery"` and `data/` contains planted credentials — all deliberate, fake, and
load-bearing for the tests, but GitHub's secret scanner will not know that. Private repo is the
easy answer. And `out/` is git-ignored on purpose: it holds the sqlite DB, the simulated access
logs and the upload drops, which are regenerated by `tools/run_all.py`.

## 5. If you want *me* to push to GitHub directly

Then I need write access to the remote, which means a credential. What I will not do is use the
token that was pasted into this conversation earlier: a secret in a transcript is a leaked secret,
and the whole point of flagging it was that you revoke it and never reuse it. If you do want this
repo pushed from my side, create a fresh **fine-grained** token scoped to that single repository
with *Contents: Read and write* and an expiry of one day, and revoke it the moment the push is done.
Say the word and I will push `main`, tag the release, and leave the bundle in place for laptops that
have no network.

## 6. What I do on my side each time (so you can check me)

```bash
git add -A && git commit -m "..."
git bundle create lab.bundle HEAD main
git bundle verify lab.bundle          # refuses to hand you something incomplete
```

`HEAD main` (not just `main`) matters: a bundle with only a branch ref clones as an empty `master`
and that is a maddening first five minutes. `git bundle verify` is how I know the file is self-
consistent before I tell you it exists.

## 7. Line endings, the one Windows trap in here

`.gitattributes` in the repo root pins `* text=auto eol=lf` and marks `*.pcap`/`*.bundle` binary.
That is why `proxy_lab/chain_demo.sh` runs under Git Bash after a checkout (a `set -u\r` would
otherwise kill it), and why pulling can never corrupt `data/lab_capture.pcap` — the pcap parser reads
byte offsets, and a "helpful" CRLF translation would silently break the whole detection module.
If you add your own files and `git status` says they are modified when you have not touched them,
run `git add --renormalize .` and commit; that is the normal cure.
